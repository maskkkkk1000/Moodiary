# Moodiary architecture and data contracts

The authoritative scope is `Moodiary_Codex_Master_Plan.md`. The current application uses Kotlin, Material 3 Compose, Navigation Compose, Hilt, Room, DataStore, WorkManager and coroutines/Flow. Minimum Android 8 (API 26), target/compile API 35. No tracking/advertising SDK or server account.

## Layers

- `domain`: immutable serializable models, statistics, search, goals, streaks, achievements, reminder date calculations, archive schema validation, streaming archive staging and JSON/CSV serialization. JVM tests do not require Android.
- `core/database`: actual Room entities, foreign keys, indexed queries, schema exports and DI. `data/repository/JournalRepository` owns transactions and serializes multi-table mutations. Parent customization uses Room Upsert (not SQLite REPLACE) to preserve child references.
- `core/datastore`: DataStore appearance/backup/lock preferences and app-private AtomicFile editor drafts.
- `core/media`: private image copies; no persistent dependency on picker URI permissions. Safe managed filename validation; abandoned imports have a 24-hour cleanup grace period. Durable draft references are always retained; deleted-entry photos with no remaining journal/draft owner are removed immediately under the repository lock.
- `core/security`: salted PBKDF2-HMAC-SHA256 (310,000 iterations), constant-time hash comparison and persisted attempt throttling. Android BiometricPrompt is optional; unavailable biometrics fall back to PIN. A new process locks immediately. App lock does not claim database encryption.
- `core/backup`: private-disk staging, validated restore and recovery, optional Google Drive provider, WorkManager automatic backups. Cloud code never enters Room's contract.
- `core/export`: structured JSON, RFC 4180 CSV, paginated Android PDF reports using platform font fallback and optional downsampled photos.
- `feature`: lifecycle-aware state collection, ViewModels, editor, management, calendar, timeline, goals, statistics and data tools. Expensive analytics/filtering/grouping run off the UI thread.

## Schema and history

Version 1 is the first baseline. Iteration 1 adds schema 2 with explicit `MIGRATION_1_2`, registered in `DatabaseModule`. It creates only `binary_goals` and `binary_goal_records` and their indices; all 13 original table definitions remain unchanged. Both schema JSON files are retained. The migration device test populates every original table, compares every column after upgrade and checks settings and private photo bytes. Unsupported upgrade/downgrade must fail instead of erasing journal content. There is no destructive fallback.

Entry primary keys are independent generated IDs. Instants use epoch milliseconds; entry mood name, score, color and icon are snapshotted to preserve historical meaning across customization. Mood/activity archival retains referenced objects. Entry deletion cascades only owned relation/photo rows; private photo cleanup is separate. One completion per goal/local-date is enforced by a unique index. Manual completions survive schedule changes as history; metrics count eligible dates only. Linked completions are recalculated transactionally after entry/goal mutations and on foreground/timezone changes.

Timestamp and mood indices support timeline/date queries; activity relation and goal completion indices match reverse joins and date reads. A keyset timeline query is available and tested. Current screen state materializes a consistent journal snapshot on a worker thread; LazyColumn renders visible rows and relation lookup maps avoid per-card full scans. Device measurements and remaining scale limits are recorded in the final verification report.

## Dates and statistics

Instants are displayed in the current device timezone; travel can move a historical entry to another day. Goal/important-day dates retain local-date semantics. Date range reads use half-open midnight-to-next-midnight instant boundaries, including DST. DST gaps in edited entry times are rejected; new overlap times use the earlier offset. Editor drafts persist their original displayed time so editing a note without changing that field preserves the original instant even after a timezone change (including seconds/overlap offset). Repository revision timestamps stay monotonic across device-clock rollback, and stale editor versions are rejected inside the write transaction. Supported dates are years 0001–9999.

Statistics preserve raw entry scores. Daily trend = mean of entries on that day. Weekday means weight each recorded day equally. Activity frequency counts entries and separately exposes recorded-day counts. Same-entry association compares entries with/without an activity. Next-day association uses only adjacent observed local-day pairs entirely inside the selected range; source dates are deduplicated and missing days are not imputed. The baseline is next-day means after recorded source days without the activity. Heuristic confidence uses the smaller comparison group (under 5, 5–14, 15–29, 30+). It is not a confidence interval or causal inference. Pair exploration is bounded to the 24 most frequent activities.

Daily/weekday streaks count scheduled dates. Weekly goals count distinct completed dates in Monday-based weeks, at most one completion per date. An incomplete current day/week does not erase the preceding streak while that period remains open. Current-period completion rates include the current period's target; partial first/last weeks use the configured weekly target. These product semantics are covered by tests, including inclusive end dates. Metrics count opportunities arithmetically and inspect recorded completions; they never enumerate millennia of unrecorded dates.

Binary goals remain independent of scheduled habit goals. Each `(goalId,date)` is unique; 1 means success, 0 means explicitly failed, and no row means unset. Completion rate is success divided by recorded outcomes, never calendar days. Available days begin at creation or the earliest explicit backfill; archive preserves history. A goal with outcomes cannot be deleted. Totals cover the selected date range, while trends display at most 104 weeks and 36 months.

Statistics filters are device-local DataStore preferences. Date, mood OR-selection and activity OR-selection jointly filter entries before calculation. Independent goal systems follow date and goal selections, not diary mood/activity selections. `StatisticsViewModel` coalesces rapid changes, computes only selected modules on `Dispatchers.Default`, and exposes loading/error states. Normal startup selects the newest valid disk draft or a new editor after recovery completes. Explicit reminder destinations take priority; recreation and app unlock retain navigation state.

## Backup and restore protocol

The archive database member uses compact streaming JSON; standalone JSON export retains indentation. Both encodings have the same data format. The 64 MiB uncompressed database limit still applies.

Format version 2 ZIP: metadata, database JSON (including binary goals and outcomes), settings JSON, managed `photos/` files. Readers accept formats 1 and 2; absent binary arrays in a legacy backup default to empty. Metadata includes SHA-256 per image. JSON rejects unknown fields/future format versions, duplicate IDs/goal dates, invalid references and unsupported values. ZIP validation rejects traversal, duplicate/unexpected members, missing media, size-limit violations and CRC/hash failures. Production restore uses a central-directory-aware ZipFile and streams photos to private staging files. Limits: 2 GB archive/expanded content, 64 MB database JSON, 32 MB per photo, 20,003 members. Older apps cannot read format 2 or schema 2; downgrade is unsupported.

Restore first validates the entire incoming archive and image decodability. Under the repository's exclusive writer lock it creates and fsyncs a rollback archive, writes an fsynced recovery marker, stages images under fresh filenames, atomically replaces Room content, applies portable settings, then removes the marker. Old media is not removed during the transaction. Failure restores the previous DB/settings. On process interruption the next launch recovers the rollback archive before exposing the journal. If recovery fails, a durable-marker guard blocks ordinary repository writes and exports, and the app shows recovery/retry. Background archive creation must first recover pending state. No later user write can be silently overwritten by a deferred rollback. Successful restore disables automatic destinations and biometrics to avoid surprising uploads/device-specific grants. The existing local PIN remains.

Backups are unencrypted sensitive files. PIN hashes, biometric state, OAuth tokens and SAF grants are not portable. No access tokens are stored by Moodiary. Optional Drive requests only `drive.appdata` via the current AuthorizationClient API. Daily Drive names are updated by ID on retry and seven successful dated versions retained. Local automatic backups stage and hash-verify bytes before renaming to a stable UTC-date filename. One successful local copy per day prevents duplicate local copies on cloud retry; seven dates are retained. Providers must support creation, readback, rename and deletion. Drive listings page through all results; disconnect revokes the short-lived token via Google’s OAuth revocation endpoint and clears its platform cache.

## Operational caveats

WorkManager reminders are approximate wall-clock reminders, not exact alarms; battery policy may defer them. Unique occurrence identifiers deduplicate retries without suppressing the following date’s notification. Matching delayed work is retained for six hours. An independent hourly repair worker and time/timezone broadcasts repair scheduling without opening the UI. Notification permission is user-controlled. Google OAuth configuration and a consenting test account are required to verify real cloud upload/download. Release signing remains the app owner's responsibility.
